# V0.12 — Competing Refinement, Source Health, Runtime Cleanup, and Live Testing

V0.12 is a refinement release. It improves how MTG Ultimate chooses upgrades, interprets tournament evidence, handles source outages, exposes the current MCP server, and now verifies key integrations through a dedicated live smoke test.

## 1. Competing upgrade packages

V0.11 iterated one candidate package at a time. V0.12 can generate several materially different packages for the same refinement round.

The default is three candidate packages per round. The caller can request 1–6.

For every candidate package the engine:

1. starts from the same accepted full deck,
2. keeps Commander legality, protected cards, exclusions, printing-family restrictions, and price constraints active,
3. uses the same simulation seed for direct candidate comparison,
4. rebuilds and resolves the complete proposed deck,
5. rejects unresolved/illegal packages,
6. rejects total-budget failures when a total budget is supplied,
7. rejects material simulated regressions,
8. calculates the V0.11 within-deck improvement heuristic,
9. selects the highest-scoring eligible package, with lower estimated spend as a tie-breaker.

Later candidate packages temporarily exclude part of the additions used by earlier candidates. This forces exploration of alternative upgrade paths instead of repeatedly simulating the same package.

The score remains a comparison heuristic. It is not a universal Commander power score or measured multiplayer win rate.

## 2. Precons and from-scratch decks use the same competition loop

`refine_precon_v12` starts from the exact MTGJSON stock list.

`build_and_refine_commander_deck_v12` first creates a legal deck draft and then runs competing-package refinement on that draft.

Themed printing policies continue through every round. For example, a Final Fantasy-only request may consider an Oracle card only when the selected incoming physical printing qualifies under the Final Fantasy printing-family policy, including allowed promos/special releases when enabled.

## 3. Tournament evidence and deduplication

V0.12 contains a conservative structured-record deduplication layer. It can collapse likely duplicate records when they share strong context such as:

- same event ID and player,
- same normalized event and player,
- same event and deck link,
- same event/player/commanders/result record.

A reused deck URL alone is **not** treated as a duplicate. Players frequently reuse a maintained Moxfield/Archidekt list across multiple events.

The output can report both raw structured record count and effective unique record count. Reference-only sources are never counted as extra structured appearances.

### EDHTop16 live-test correction

Earlier V0.9/V0.12 code treated the legacy EDHTop16 filtered POST API as structured tournament evidence. The new live integration suite tested those routes directly in August 2026.

The public site remained reachable, and an old `get_commanders` GET path was reachable on a legacy host, but the filtered POST routes used for `req`/tournament queries redirected to the public EDHTop16 homepage and returned HTML rather than structured JSON.

MTG Ultimate therefore now treats EDHTop16 as **attributed public competitive-reference evidence**, not as a working structured backend dependency. The compatibility helper returns a reference packet with no invented entries. If a current stable structured endpoint is verified later, it can be promoted back deliberately.

TopDeck.gg remains the structured tournament-results path when its API key is configured.

## 4. Source-health diagnostics

`source_health_v12` actively checks the structured integrations MTG Ultimate can currently probe and rely on:

- Scryfall,
- Commander Spellbook,
- MTGJSON,
- TopDeck.gg when an API key is configured.

EDHTop16 is returned as `reference-only` rather than `degraded`, because the retired legacy POST endpoint is no longer considered a required backend.

Other reference-only sources such as Wizards, EDHREC, Moxfield, DeckCheck, and TCGfind NZ are separately labelled so a missing private API is not confused with an outage.

Safe GET/HEAD requests benefit from the V0.11 bounded retry layer. Read-oriented POST APIs are probed once by diagnostics so a broken endpoint is not hidden by repeated POST attempts.

A source outage must lower confidence or trigger another evidence path; it must never cause invented card/rules/deck data.

## 5. Runtime/server cleanup

Earlier releases grew through numbered registration modules. V0.12 cleans up the active boundary without doing a dangerous all-at-once rewrite of working historical registration code.

- `src/server-current.ts` is the stable application entry for the current MCP server.
- `src/index.ts` depends on `server-current` instead of importing a numbered release directly.
- The base `McpServer` constructor uses `config.version` rather than the old hard-coded `0.4.0` string.
- Package version, health endpoint, User-Agent, and MCP server identity therefore derive from the same release version.
- Historical `server-v04` … `server-v11` modules remain available as compatibility/regression layers while the active entry point is stable.
- V0.12 exposes its own `registerMtgToolsV12(server)` registration function, which is the preferred pattern for future tool sets.

This is deliberate incremental flattening: the public/runtime entry and version identity are flattened now, while old registration modules are retained until they can be consolidated with equivalent regression coverage.

## 6. New tools

### `refine_commander_deck_v12`
Compare several upgrade packages per round and iteratively refine an existing legal Commander deck.

### `refine_precon_v12`
Apply the same competing-package optimization to any supported stock Commander precon.

### `build_and_refine_commander_deck_v12`
Build a legal deck from scratch and optimize it with competing packages.

### `source_health_v12`
Report structured-source health/configuration while keeping reference-only websites distinct from backend APIs.

### `cross_reference_tournament_evidence_v12`
Use structured TopDeck evidence when configured, pair it with public competitive-reference context such as EDHTop16, and deduplicate structured records that are actually available.

## 7. Live integration testing

The normal suite remains:

```bash
npm run check
```

A separate live smoke suite is available:

```bash
npm run test:live
```

The live suite intentionally hits current external services instead of mocks. It checks:

- Scryfall resolves `Sol Ring` and reports Commander legality,
- Commander Spellbook responds,
- MTGJSON responds,
- the live Commander precon catalog contains `Limit Break`,
- stock `Limit Break (FINAL FANTASY VII)` resolves to exactly 100 cards,
- exact set / collector-number / finish identity is preserved in the stock list,
- EDHTop16 is represented as reference-only rather than as a fabricated healthy structured API.

`.github/workflows/live-smoke.yml` runs this separately from normal CI. That separation matters: a third-party outage can fail the live integration workflow without being mislabeled as a TypeScript/unit-test regression.

The first live smoke pass immediately found the stale EDHTop16 API assumption, demonstrating why this layer is kept in addition to the normal unit suite.

## 8. Output philosophy

Simple remains the default. A normal upgrade answer should lead with exact OUT -> IN swaps, selected printing, estimated spend, and a short reason.

Detailed mode can show candidate-package comparisons, why losing packages were rejected, structured tournament sample counts, public-reference context, and source-health details.

The complexity belongs underneath the answer, not in the user's way.
