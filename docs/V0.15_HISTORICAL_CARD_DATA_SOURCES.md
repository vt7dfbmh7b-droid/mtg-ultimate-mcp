# V0.15 Historical Card-Data Source Inventory

Audit date: 2026-08-20

This document records the source decision behind the first provenance-safe historical card-data acquisition primitive. It does **not** promote V0.15, change `server-current`, or establish that any current feed is a retrospective historical archive.

## Safety requirement

Historical predictor features may use Oracle text, type line, mana value, printing identity, release date and Commander legality only when the exact source contents are independently shown to have been available by the requested feature cutoff.

A source is not historical merely because individual cards have old release dates. A file fetched today may contain later Oracle text, legality changes, new printings or other future knowledge.

## Source inventory

### Scryfall bulk data

Primary use: current structured card/printing data.

Current mechanism:

- `https://api.scryfall.com/bulk-data` identifies current bulk exports.
- `default_cards` is the natural physical-printing feed for the existing Scryfall-shaped feature pipeline.
- Scryfall recommends bulk downloads for large local card-data workloads rather than large numbers of live API lookups.

Historical decision:

- No official replayable daily-history/archive contract has been verified for arbitrary past dates.
- A current Scryfall bulk file must therefore be treated as **current data observed now**, not as proof of an older predictor state.
- It is suitable for a forward contemporaneous-capture pipeline when the exact downloaded bytes, observation time, source URI and SHA-256 are preserved.

### MTGJSON

Primary use: current downloadable card databases and a possible second structured source.

Verified current properties from MTGJSON documentation:

- the public API data is rebuilt daily;
- `Meta.json` exposes the build date and version;
- MTGJSON v5 publishes SHA-256 validation sidecars for downloadable files;
- `AllPrintings` contains printing-level card data.

Historical decision:

- The documented current file server is not, by itself, proof of a replayable daily historical archive.
- Sparse software/release tags are not equivalent to daily card-data snapshots.
- Until an independently replayable historical file path is verified, current MTGJSON data must also remain contemporaneous/current-only for predictor provenance.
- MTGJSON is not wired into the first acquisition adapter because its native schema differs from the existing Scryfall card contract; adding that adapter without a historical archive would not solve the blocker.

## Implemented acquisition contract

`historical-carddata-acquisition-v15.ts` adds two deliberately separate paths.

### 1. Pinned archived snapshot replay

`acquirePinnedHistoricalCardDataV15` requires an already-audited archive pin containing:

- source ID;
- exact source URI;
- SHA-256 content hash;
- archive version;
- snapshot effective time;
- archive publication time;
- Scryfall-card-array format identity;
- optional exact byte length.

Before network access, the existing historical provenance assessment must accept the archive publication/effective times for the requested feature cutoff. The download is then bounded, exact bytes are hashed, optional byte length is checked, UTF-8/JSON is validated, and every row must satisfy the required Scryfall card shape.

A pin is **not** permission to invent publication metadata. Callers may create archive pins only from a separately audited source/version record. No production retrospective archive is registered by this milestone.

### 2. Forward contemporaneous capture

`captureCurrentCardDataV15` downloads a current Scryfall-shaped card array and assigns the observation time at capture. It computes the SHA-256 from the exact received bytes; callers cannot provide an older `observedAt` through the source descriptor.

The captured data can later feed `extractDeckFeatureSnapshotFromCapturedCardDataV15`, but the existing provenance gate still rejects any requested feature cutoff earlier than the capture time. This is intentional: current data can support future observations without being backdated into past TopDeck outcomes.

## Predictor integration

`extractDeckFeatureSnapshotFromHistoricalCardDataV15` wires verified pinned archive acquisition directly into the existing `extractProvenancedDeckFeatureSnapshotV15` path. Historical printing resolution and the dated Commander construction validator therefore remain mandatory after acquisition.

The current 4,395 TopDeck candidates are **not** made historically trainable by this change. Without a verified archive published by each candidate's predictor cutoff, they remain unavailable for rich historical features rather than receiving current card data.

## Next source work

1. Continue searching for an independently replayable, versioned historical card-data archive with publication timestamps and immutable/pinned bytes.
2. If none is adequate, add a retained forward capture job that stores exact bulk bytes (or a content-addressed immutable object), source metadata and SHA-256 on a regular schedule.
3. Add a live source-audit workflow only after a concrete provider/archive contract exists; live CI must distinguish source outage from provenance failure.
4. Once trusted snapshots exist for real TopDeck candidates, measure usable versus unavailable coverage before fitting any model.

V0.15 remains experimental and shadow-only. Stable promotion remains an explicit later user decision.
