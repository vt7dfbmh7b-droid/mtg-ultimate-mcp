FAST EXECUTION / RECOVERY PATH

This section supplements all preceding instructions. It cannot override, weaken, shorten, rewrite, reorder, collapse, discard or change the precedence of any preceding instruction, quality gate or authority boundary. If an optimization conflicts with a required step, perform the required step. The 50% efficiency target never creates an exception.

1. Recover once, with verified evidence. Read project-state.json first and AGENTS.md immediately afterward. Complete every recovery inspection required above and by the repository handoff protocol. Batch independent reads against the same observed commit where possible. Use targeted historical sections only where the existing protocol permits; never omit a required document or claim a truncated response was fully read. Retain an invocation-local map of the branch head, accepted baseline, tested/validated/frozen SHA, relevant evidence references, candidate status, completed stage, unfinished gate and exact next action. Reuse unchanged content during that invocation. Refresh affected evidence whenever the head, inputs, authority, validation state or writers change; investigate conflicts or missing evidence before relying on the map.

2. Advance from the first unfinished required stage. Compare nextActions with newer commits, actual test logs and durable manual verdicts so an already-proven failing regression is not rediscovered or re-added because a handoff lags. Reconcile material lag under the existing rules. Reuse only the scope the evidence proves: a focused failing regression does not complete all remaining regressions; a green suite is not manual acceptance. Keep the accepted baseline distinct from a tested or formally validated candidate. Switch tasks only when the current action is complete, invalidated, blocked, unsafe or superseded by authoritative evidence.

3. Use the available invocation for consecutive gated stages. After each material result, determine whether the directly connected next stage can safely finish or leave a deterministic checkpoint. If so, continue through justified diagnosis, generic repair, focused regression, full acceptance validation, freeze, required unchanged replay, complete-deck review, comparison and generalization as their prerequisites are actually satisfied. Do not stop solely because a commit, test or fixture completed. Do not delay required material checkpoints or cross an unfinished gate to combine stages. Before every branch-changing operation, refresh the head and all relevant writers, including jobs from earlier commits. Preserve single-flight rules. While a writer runs, use safe read-only review of persisted evidence relevant to the same sequence if available. Wait for the approved writer and verify its resulting head before dependent writes; checkpoint if capacity or authority requires deferral.

4. Avoid optional duplicate validation. During diagnosis, use the smallest production-path regression that resolves the concrete uncertainty when the existing rules permit. Do not explicitly dispatch a duplicate suite or replay while its required execution already exists or remains valid. Never suppress automatic CI, change workflow triggers, use skip flags to evade a gate, or modify protected workflow files, tests or policy epochs. Every product repair still requires the full mandated validation on the exact checked-in candidate, followed by every required replay and manual gate. Retain exact provenance; matching src/** alone never transfers whole-tree validation to another commit. Changes to relevant tests, scripts, dependencies, configuration, state, inputs or provider evidence may invalidate reuse. A mandated fresh execution always takes precedence.

5. Extract more quality evidence from each frozen source. Within existing replay interfaces, execution capacity and provider limits, complete several genuinely contrasting fixtures and their required whole-deck assessments/comparisons before changing intelligence. Prepare only the next useful fixtures in the same authorized batch. Do not create concurrent writers or change source mid-batch. Reference a durable prior complete-deck verdict only when the relevant product source, full deck output, request, constraints, review criteria and material provider evidence are unchanged, the verdict covers the exact question, and no fresh review is required. New or materially changed decks still receive complete review, not merely a swap-list check. Never count reused verdicts as new fixtures, unseen breadth, new comparisons or additional promotion evidence. Preserve all strong general-AI comparison requirements; do not invent an unexecuted comparator.

6. Make necessary checkpoints cheaper and complete. Use the existing synchronized state surfaces and durable manual-verdict locations, without introducing a second source of truth or changing the milestone schema. When supported by authorized direct repository tooling, prepare related material state, generated handoff, validation and roadmap changes together as one coherent commit/package instead of pushing known-incomplete intermediate states. Use checked-in generation/validation tools outside validation workflows. Preserve approved integrity-writer completion and rechecks. A checkpoint records accepted baseline, exact candidate/tested/validated/frozen SHA, candidate/provisional status, completed and incomplete stages, evidence location and exact next executable action. Do not defer material evidence until the end of an oversized batch. After necessary synchronization, return immediately to Commander-product work.

7. Pursue and measure useful gain without creating overhead. Aim seriously for at least 1.5x useful Commander progress per comparable invocation, or 50% less avoidable overhead for equivalent quality. Use existing run summaries and durable benchmark evidence to identify saved repeated recovery, repeated diagnosis, optional duplicate execution, state-sync rework and unnecessary invocation boundaries. Report completed fixtures with required review, actual comparisons, generic defects isolated, validated generic repairs, completed frozen batches and stronger deck/promotion evidence, keeping unlike outcomes separate. Do not count commits, workflows, documentation, test volume or repeated evidence as throughput. Distinguish measured gains from estimates, normalize for fixture difficulty and provider/runner delays, and avoid double-counting the same saving. No new telemetry system or documentation-only work is required. If 50% is unsupported, report the smaller evidenced gain; quality remains the objective.
